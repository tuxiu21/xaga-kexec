# 2026-07-29 Ubuntu `skb_release_data` Panic

Status: producer not identified; controlled A/B testing pending

Repository: `/home/in/work/kernels`

## Executive summary

Six controlled `./xaga boot prod` runs reached persistent kexec marker `0x51`,
entered Ubuntu and completed Wi-Fi readiness. One run later panicked in the
Ubuntu network receive path at about 111.7 seconds of kernel uptime.

The immediate crash condition is proven:

```text
skb_shared_info.nr_frags = 1
skb_shared_info.frags[0].page = NULL
```

`skb_release_data()` attempted to release the declared fragment, reached
`put_page(NULL)`, and faulted while accessing `NULL+8`.

This is a new-kernel runtime panic, not evidence that `machine_kexec()`,
`cpu_soft_restart()` or relocation failed. The component that first produced
the inconsistent skb metadata is still unknown.

For the durable marker and pstore procedure, read
[`../KEXEC_DEBUGGING.md`](../KEXEC_DEBUGGING.md).

## Panic evidence

The preserved console excerpt is tracked alongside this incident as
[`2026-07-29-skb-panic-console-reconstructed.txt`](2026-07-29-skb-panic-console-reconstructed.txt).
It is a reconstruction from two overlapping historical reads, not the original
complete `console-ramoops-0`; its header records that provenance and limitation.

The affected Ubuntu kernel was:

```text
5.10.226-android12-9-00006-g80751a7a9ff4-dirty
```

The matching unstripped symbols are:

```text
sources/android-kernel/out/android12-5.10/dist/vmlinux
```

The panic contained:

```text
Unable to handle kernel NULL pointer dereference at virtual address 0000000000000008
Internal error: Oops: 96000007
pc: skb_release_data+0xa0/0x240
lr: __consume_stateless_skb+0x28/0x18c
CPU: 7 PID: 2920 Comm: mihomo Tainted: G W O

skb_release_data
__consume_stateless_skb
skb_consume_udp
udp_recvmsg
inet_recvmsg
sock_read_iter
vfs_read
ksys_read
```

Stock reported:

```text
ro.boot.bootreason=kernel_panic
sys.boot.reason=kernel_panic,null
```

Symbolization resolved the PC through:

```text
compound_head
  -> put_page
  -> __skb_frag_unref
  -> skb_release_data
```

The release loop is at
`sources/android-kernel/common/net/core/skbuff.c:620`:

```c
for (i = 0; i < shinfo->nr_frags; i++)
        __skb_frag_unref(&shinfo->frags[i]);
```

The faulting instructions were:

```asm
ldr     x8, [x22]       // frag page pointer, observed as zero
add     x9, x8, #0x8
ldar    x9, [x9]        // fault at NULL + 8
```

Register and memory inspection established:

```text
x20 = skb_shared_info
*(u8 *)(x20 + 2) = nr_frags = 1
x22 = x20 + 0x48 = &frags[0]
frags[0] memory is zero
frags[0].page = NULL
```

The release path is where the corrupt metadata became fatal. It is not
necessarily where the skb was first corrupted.

## What is and is not established

Established:

- the kexec handoff reached the new kernel at marker `0x51`;
- Ubuntu userspace and Wi-Fi came up before the panic;
- Mihomo consumed the UDP skb through `recvmsg()`;
- the skb declared one page fragment whose page pointer was null;
- the fixed-name pstore must be collected before another kexec.

Not established:

- Mihomo created the invalid skb;
- GRO alone created it;
- the vendor Wi-Fi driver alone created it;
- a specific newer Android shared-frag/GSO commit fixes it;
- rebuilding the current `xaga-ubuntu` branch fixes it.

## ABI check

A simple stock/Ubuntu skb layout mismatch is not supported. DWARF comparison
gave identical layouts:

```text
sizeof(struct sk_buff) = 0xf0
sizeof(struct skb_shared_info) = 0x158
offsetof(nr_frags) = 0x02
offsetof(frags) = 0x48
```

## Current producer hypotheses

In descending order of current plausibility:

1. vendor Wi-Fi RX and software GRO incorrectly transfer, aggregate or release
   a fragment under heavy UDP traffic;
2. GRO plus Mihomo system TUN/fake-IP/UDP traffic triggers a core-network or
   vendor interaction;
3. an earlier out-of-bounds write or use-after-free corrupts the shared info and
   only becomes visible during release;
4. the Android GKI 5.10.226 baseline lacks a relevant later shared-frag/GSO
   correction.

Conditions during the failing workload included:

```text
vendor module: wlan_drv_gen4m_6895
module status: out-of-tree
kernel taint: W O
wlan0 software GRO: on
wlan0 rx-gro-hw: off
mihomo: system TUN and fake-IP DNS
traffic: UDP, DNS, NTP and Hysteria2
```

## Next controlled experiments

Change one variable at a time. Each group should use at least ten bounded boot
rounds and hold realistic network load for 30 to 60 minutes after Wi-Fi READY.
Stop and archive pstore on the first failure.

### A: Mihomo on, wlan0 software GRO off

This is the first experiment.

```bash
ssh xaga 'sudo ethtool -K wlan0 gro off'
ssh xaga 'ethtool -k wlan0 | grep -E "generic-receive-offload|rx-gro-hw"'
ssh xaga 'systemctl is-active mihomo'
```

If this is stable while a comparable baseline reproduces the panic, the search
narrows toward GRO or the vendor Wi-Fi/GRO boundary. A failure with the same
signature prevents that conclusion.

### B: GRO on, Mihomo stopped

```bash
ssh xaga 'sudo ethtool -K wlan0 gro on'
ssh xaga 'sudo systemctl stop mihomo'
ssh xaga 'ethtool -k wlan0 | grep -E "generic-receive-offload|rx-gro-hw"; systemctl is-active mihomo || true'
```

Generate comparable UDP/Wi-Fi pressure without Mihomo. A quiet network is not a
valid comparison. Restore the service afterwards:

```bash
ssh xaga 'sudo systemctl start mihomo'
```

### C: Instrument the first invalid-frag boundary

Do not only guard `skb_release_data()` and treat the absence of a panic as a
fix. Add debug-only validation at:

- vendor Wi-Fi RX skb construction;
- GRO receive, merge and complete boundaries;
- skb clone/copy/fragment transfer boundaries;
- UDP enqueue;
- final skb release.

Record skb address, users, head, data, len, data_len, nr_frags, fragment
page/offset/size and a stack trace. Use ratelimiting, `WARN_ON_ONCE()` or a
bounded trace buffer to avoid log flooding. A null-page release guard may keep
the device alive for diagnosis, but it only masks the fatal dereference.

### D: Establish a newer 5.10 baseline separately

Evaluate a later Android 5.10 baseline on a new Ubuntu kernel branch. Do not
bulk-merge candidate changes into the current validation branch. Revalidate
KMI/vendor modules, Wi-Fi, the same GRO/Mihomo workload, and equal soak time.
